## 1. Core Song Metadata Model

MyKey SightPlay maintains a two-layer metadata system:

**Layer 1 — Song JSON (`songs/*.json`)**
Authoritative source. All derived index fields originate here. Owned by the import pipeline.

**Layer 2 — Song Index (`songs/index.json`)**
Runtime-readable catalog. Contains a subset of fields from Layer 1 (derived) plus curation decisions made by the operator (curation). Regenerated by `tools/update_song_index.py`.

**Field ownership rule:**

| Ownership | Behavior |
|-----------|----------|
| Derived   | Always overwritten from `song.json` on `update_song_index.py` run |
| Curation  | Set by operator; preserved across tool re-runs |

The distinction is critical: curation decisions (which collection a song belongs to, whether it is publicly listed) must survive metadata corrections to the underlying `song.json`.

---

## 2. Required Fields

Fields that must be present and non-empty in every valid index entry.

| Field  | Type    | Ownership | Source               | Description |
|--------|---------|-----------|----------------------|-------------|
| `src`  | string  | derived   | file path            | Relative URL path to the song.json file. Format: `songs/<filename>.json`. Serves as the stable identifier within the index. |
| `label`| string  | derived   | computed             | Auto-generated composite string for human-readable display in dropdowns and lists. Format: `{title} — {time_sig} · {bpm} BPM · {bar_count} bars [· optional tags]`. |

**Label tag inclusions (appended only when applicable):**
- `pickup` — when bar 1's first beat is not beat 1
- `Key {key}` — when key signature is not C major
- `segments` — when `learning_segments` array is non-empty

---

## 3. Optional Fields

Fields that may be null or absent. The index always includes them (with `null` value), so consumers can read without defensive checks.

| Field          | Type          | Ownership | Source                     | Description |
|----------------|---------------|-----------|----------------------------|-------------|
| `title`        | string\|null  | derived   | `meta.title`               | Human-readable song title. Null when `meta.title` is a placeholder value ("Untitled score", "Untitled", ""). Falls back to filename stem during label generation only. |
| `composer`     | string\|null  | derived   | `meta.composer`            | Composer name. Null when `meta.composer` is a placeholder value ("Composer / arranger", "Composer/arranger", ""). |
| `level`        | string\|null  | derived   | `meta.level`               | Pedagogical difficulty. Valid values: `early_beginner`, `beginner`, `intermediate`, `advanced`. |
| `collectionId` | string\|null  | curation  | operator assignment        | Foreign key into `collections.json`. Null means the song is not assigned to any collection. |
| `listed`       | boolean       | curation  | operator decision          | Public visibility flag. `true` = appears in student-facing Song Browser. `false` = internal fixture or teacher-assigned only. Default on first import: `false` for filenames starting with `test_` or matching known fixture stems; `true` for all other files. |
| `tags`         | string[]      | curation  | operator assignment        | Song-level tag overrides using the controlled vocabulary prefix convention (see Section 5). Empty array by default. |

**Placeholder values — production guard:**

The following values are treated as absent and normalized to `null` in the index:

| Field      | Placeholder values (case-insensitive) |
|------------|---------------------------------------|
| `title`    | `""`, `"untitled"`, `"untitled score"` |
| `composer` | `""`, `"composer / arranger"`, `"composer/arranger"` |

Songs whose `title` resolves to `null` must not be set to `listed: true` until `meta.title` is corrected in the source `song.json`.

## 4. Searchable Fields

Fields exposed to Song Browser search and filter UI. All searchable fields must be present in `index.json` entries — no secondary fetch required for browsing.

| Field          | Search Type     | Filter Type | Notes |
|----------------|-----------------|-------------|-------|
| `title`        | full-text       | —           | Primary search target |
| `composer`     | full-text       | —           | Secondary search target |
| `level`        | —               | enum select | Values: `early_beginner`, `beginner`, `intermediate`, `advanced` |
| `collectionId` | —               | FK lookup   | Resolves to collection name via `collections.json` |
| `listed`       | —               | boolean     | Always applied as a pre-filter in student-facing UI |
| `tags`         | prefix-match    | multi-select| See tag prefix vocabulary in Section 5 |

**Tag prefix vocabulary:**

Tags use a `prefix:value` convention to enable structured filtering. No free-form tags are permitted in production entries.

| Prefix    | Meaning                           | Example values |
|-----------|-----------------------------------|----------------|
| `cat:`    | Pedagogical category              | `cat:technique`, `cat:repertoire`, `cat:sight-reading` |
| `genre:`  | Musical style or genre            | `genre:classical`, `genre:folk`, `genre:pop` |
| `origin:` | Geographic or cultural origin     | `origin:indonesia`, `origin:europe`, `origin:usa` |
| `period:` | Historical period                 | `period:baroque`, `period:romantic`, `period:contemporary` |
| `skill:`  | Technical skill targeted          | `skill:legato`, `skill:scale`, `skill:arpeggio` |
| `format:` | Content format type               | `format:exercise`, `format:piece`, `format:etude` |

Tags at the song level override or supplement tags inherited from the collection. If a song has no tags, its effective tags are those of its collection.

## 5. Collection Relationship Model

Collections are the primary structural entity for organizing songs. A collection is a named, ordered group of songs from a common provider (book, curriculum, or content series).

### `collections.json` schema

```
songs/collections.json
```

```json
{
  "version": 1,
  "collections": [
    {
      "id": "beyer-op101",
      "name": "Beyer Op.101",
      "provider": "public-domain",
      "listed": true,
      "order": 1,
      "tags": ["cat:repertoire", "format:exercise", "period:romantic"]
    }
  ]
}
```

### Collection fields

| Field      | Type     | Required | Description |
|------------|----------|----------|-------------|
| `id`       | string   | yes      | Stable slug. Kebab-case. Never changed after first use — songs reference it by this key. |
| `name`     | string   | yes      | Human-readable display name shown in Song Browser. |
| `provider` | string   | yes      | Provider ID. References a provider in the `providers` array (see Section 6). |
| `listed`   | boolean  | yes      | If `false`, the entire collection is hidden from the public Song Browser even if individual songs have `listed: true`. |
| `order`    | integer  | yes      | Display sort order within the Sight Reading category. Lower is first. |
| `tags`     | string[] | no       | Collection-level tags. Inherited by songs in this collection unless the song overrides. |

### Collection → Song relationship

- One collection contains zero or more songs.
- One song belongs to at most one collection (`collectionId` in `index.json`).
- Songs with `collectionId: null` are uncollected — they may appear as standalone entries if `listed: true`.
- The Song Browser groups listed songs by their collection. Uncollected listed songs appear under a "Standalone" group.

### Collection visibility rules

A song is visible in the student-facing Song Browser if and only if:
1. `song.listed === true`, AND
2. `collection.listed === true` (for songs with a `collectionId`), AND
3. User has access (guest, assigned, or public — evaluated at runtime by `access.js`).

Unlisted songs remain accessible via direct URL or teacher assignment link regardless of the `listed` flag.

## 6. Provider Relationship Model

A provider is a content source: a publisher, curriculum series, or rights holder. Provider is a separate concern from collection — a provider may have multiple collections.

### Provider registry in `collections.json`

Providers are embedded in `collections.json` as a top-level array:

```json
{
  "version": 2,
  "providers": [
    {
      "id": "public-domain",
      "name": "Public Domain",
      "listed": true,
      "requiresAssignment": false
    },
    {
      "id": "yamaha",
      "name": "Yamaha Music Education",
      "listed": false,
      "requiresAssignment": true
    }
  ],
  "collections": [...]
}
```

### Provider fields

| Field                | Type    | Required | Description |
|----------------------|---------|----------|-------------|
| `id`                 | string  | yes      | Stable slug. Referenced by `collection.provider`. |
| `name`               | string  | yes      | Display name for admin UI. Not shown to students. |
| `listed`             | boolean | yes      | If `false`, all collections from this provider are excluded from the public Song Browser. |
| `requiresAssignment` | boolean | yes      | If `true`, songs from this provider are only accessible via teacher assignment, even if `song.listed: true`. |

### Provider visibility cascade

```
provider.listed = false
  → all collections in this provider are hidden
      → regardless of collection.listed
          → regardless of song.listed
```

```
provider.requiresAssignment = true
  → songs are only accessible via assignment link
      → student cannot browse or self-assign
```

This cascade allows a single flag change to gate an entire licensed curriculum without modifying individual song entries.

### Content licensing model

| Provider type          | `listed` | `requiresAssignment` | Access                    |
|------------------------|----------|----------------------|---------------------------|
| Public Domain          | true     | false                | Public, appears in Explore |
| Licensed (school book) | false    | true                 | Teacher-assigned only      |
| Internal fixture       | false    | false                | Developer access only      |

## 7. Future Compatibility — Song Browser

The metadata model is designed to support a student-facing Song Browser (`library.html`) without schema changes.

### Song Browser data requirements

| Feature                        | Field(s) required          | Available now? |
|-------------------------------|----------------------------|----------------|
| Search by title                | `title`                    | Yes            |
| Search by composer             | `composer`                 | Yes            |
| Filter by level                | `level`                    | Yes            |
| Filter by collection           | `collectionId` + `collections.json` | Yes   |
| Filter by tag / category       | `tags`                     | Yes            |
| Hide internal fixtures         | `listed`                   | Yes            |
| Hide unlicensed content        | `provider.listed`, `provider.requiresAssignment` | Yes |
| Sort by collection order       | `collection.order`         | Yes            |
| Display collection name        | `collection.name`          | Yes            |
| Display composer               | `composer`                 | Yes            |

### Song Browser architecture constraints

- The browser must fetch `songs/index.json` and `songs/collections.json` on load — no per-song fetch during browsing.
- All data needed to render the browse grid must be present in those two files.
- Song content (the `song.json` file) is fetched only when the student opens a specific song.
- The `listed` pre-filter must be applied before rendering. Never expose `listed: false` entries in the student UI.

### Planned Song Browser URL model

```
/library.html
/library.html?collection=beyer-op101
/library.html?level=early_beginner
/library.html?tags=cat:technique
/library.html?q=london+bridge
```

These URL parameters map directly to `index.json` fields and require no schema additions.

## 8. Future Compatibility — Import Tool

The metadata model supports a batch import workflow without schema redesign.

### Import pipeline (current)

```
MuseScore → Export MusicXML → mxl_to_song.py → song.json → songs/ directory
                                                            ↓
                                                  update_song_index.py
                                                            ↓
                                                      index.json
```

### Import tool responsibilities

| Step | Tool | Action |
|------|------|--------|
| 1    | `mxl_to_song.py`        | Convert MusicXML → `song.json`. Writes `meta.title`, `meta.composer`, `meta.level`, `meta.bpm`, `meta.time_signature`, `meta.key_signature`. |
| 2    | `validate_song.py`      | Validate structural correctness. Must pass before proceeding. |
| 3    | Song Manager UI         | Operator sets `listed`, `collectionId`, `tags` (curation fields). |
| 4    | `update_song_index.py`  | Regenerate `index.json`. Derived fields overwritten from `song.json`. Curation fields preserved. |

### Import guard rules

The import tool must enforce these checks before writing to the `songs/` directory:

| Check | Field | Rule |
|-------|-------|------|
| No placeholder title | `meta.title` | Must not be in placeholder set |
| No placeholder composer | `meta.composer` | Must not be in placeholder set (or must be explicitly null) |
| Valid level | `meta.level` | Must be one of: `early_beginner`, `beginner`, `intermediate`, `advanced` |
| Unique filename | file stem | Must not conflict with existing files |
| Valid collection | `collectionId` | Must reference an existing collection ID in `collections.json`, or be null |

Songs that fail any guard must not be set to `listed: true`. They are imported as `listed: false` and flagged for operator review.

### Planned import workflow document

`docs/import/import-workflow.md` — to be written. Will cover:
- MuseScore export settings
- `mxl_to_song.py` invocation
- `validate_song.py` invocation and error interpretation
- Song Manager curation steps
- `update_song_index.py` regeneration
- Publish checklist (listed flag, collectionId, tags, title, composer)

## Appendix — Field Summary Reference

### Per-song fields in `index.json`

| Field          | Type          | Ownership | Required | Searchable |
|----------------|---------------|-----------|----------|------------|
| `src`          | string        | derived   | yes      | no         |
| `label`        | string        | derived   | yes      | no         |
| `title`        | string\|null  | derived   | no       | full-text  |
| `composer`     | string\|null  | derived   | no       | full-text  |
| `level`        | string\|null  | derived   | no       | enum       |
| `collectionId` | string\|null  | curation  | no       | FK lookup  |
| `listed`       | boolean       | curation  | yes      | pre-filter |
| `tags`         | string[]      | curation  | no       | prefix     |

### Per-collection fields in `collections.json`

| Field      | Type     | Required |
|------------|----------|----------|
| `id`       | string   | yes      |
| `name`     | string   | yes      |
| `provider` | string   | yes      |
| `listed`   | boolean  | yes      |
| `order`    | integer  | yes      |
| `tags`     | string[] | no       |

### Per-provider fields in `collections.json`

| Field                | Type    | Required |
|----------------------|---------|----------|
| `id`                 | string  | yes      |
| `name`               | string  | yes      |
| `listed`             | boolean | yes      |
| `requiresAssignment` | boolean | yes      |
